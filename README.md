# Reach-Read Method（日本語の有価証券報告書版）

RAG が設問に正答できなかったとき、検索と読解のどちらで失敗したのかを設問ごとに突き止め、どちらを直せばよいかを示す方法です。
採点に言語モデルも人手も使わないので、誰が計算しても同じ数字になります。

このリポジトリには、日本語の有価証券報告書でこの方法を使うためのスクリプトが二つあります。

- `get_ja_data.py`：書類（有価証券報告書 2,551 通）と設問を用意する
- `rrm_ja.py`：自分の RAG の実行記録を採点し、六つのマスと「まず直す場所」を出す

## 方法

RAG は二段階で答えを出します。書類を区切った断片（チャンク）から設問に合うものを探すのが検索で、上位の数件を言語モデル（回答モデル）に読ませるのが読解です。
正答率だけを見ても、どちらの段階で失敗したかは分かりません。

Reach-Read Method は、正解が書類に印字された一つの数値である設問について、設問ごとに二つのことだけを記録します。

- **Reach**：正解の箇所が、回答モデルに渡したチャンクに入っていたか。
  正解の箇所とは、設問の対象企業の書類のチャンクのうち、正解の数値が印字されたものです。
- **Read**：回答が正答・無回答・誤答のどれか。無回答は、数値を出さずに「見つからない」と答えたものです。
  正答は、相対誤差が 0.5% 以内で、しかも回答に書かれた最後の桁で正解を丸めると一致するものに限ります。
  正解が 245,896 百万円なら、「2,459億円」は正答で「2,458億円」は誤答です。

二つを組み合わせると、どの回答も次の六つのマスのどれかに入ります。

|  | 正答 | 無回答 | 誤答 |
|---|---|---|---|
| 届いた | 届いて正答 | 届いたのに無回答（読解を直す） | 届いたのに誤答（読解を直す） |
| 届かなかった | 届かずに正答 | 届かずに無回答（検索を直す） | 届かずに誤答（検索と、回答モデルへの指示を直す） |

正解の箇所が届かなかった設問では、「見つからない」と答えるのが正しい振る舞いです。
届かなかったのに数値を答えたなら、渡されていない数値を答えたことになります。

構成（検索器・渡す量・回答モデルの組み合わせ）ごとに、正答できなかった割合を二つに分けます。
届かずに正答できなかった割合が検索の失敗で、届いたのに正答できなかった割合が読解の失敗です。
二つの差の 95% 区間（設問を単位にしたブートストラップ）が 0 をまたがなければ、大きいほうをその構成でまず直す場所とします。

## 日本語版で足したこと

考え方は英語版（米国企業の年次報告書 10-K で使ったもの）と同じです。日本語の書き方に合わせて、次の点を足しました。

- Read は、全角数字・△▲・「マイナス」・千円・百万円・億・兆を読みます。「2,458億96百万円」「75億4千5百万円」のような書き方も読みます。
  「見つかりません」「記載されていません」などは無回答に数えます。
- Reach は、4 桁以上の表記はそのまま数えます。3 桁以下の表記と丸めた表記（「2,459億円」「1兆2,293億円」「2,136百万円」など）は、すぐ前の 80 字以内に項目名があるときだけ数えます。
- 有価証券報告書の表は、元データの段階で列の区切りが消えています。前期 396,925 と当期 245,896 が「396,925245,896」とつながります。
  株主資本等変動計算書や四半期の表では、三つ以上の列がつながります。
  数字の連なりが 3 桁ごとにカンマを打った正しい形でなければ、列がつながったものとみなします。そして、両側が正しい形の数値の並びとして読める位置を列の切れ目として認めます。

## 使い方

### 1. 準備

```bash
git clone https://github.com/Hajime-Institute/reach-read-method
cd reach-read-method
python3 -m venv .venv
source .venv/bin/activate        # Windows では .venv\Scripts\activate
pip install -r requirements.txt
```

Python 3.9 以上で動きます（3.9.6 と 3.13 で確認）。ディスクは約 400 MB 使います。

### 2. 書類と設問を用意する

```bash
python get_ja_data.py --out ja_data --questions questions_ja.json --chunks
```

EDINET-Bench（Sakana AI）を論文と同じ版に固定して Hugging Face から取ります（約 112 MB、アカウント不要）。
それを有価証券報告書 2,551 通に組み直し、書類ごとのテキストに書き出します。
リポジトリの設問ファイル（`questions_ja.json`）を渡すと、この書類を検索させる日本語の設問 406 問も取り出します。
このうち Reach-Read Method で採点できるのは、一つの数値を引く JA-LOOKUP の 174 問です。
時間は取得込みで 20 秒ほどです（実測）。最後に検査の結果が出て、論文と同じ書類集合でなければ止まります。

| ファイル | 中身 |
|---|---|
| `text/<doc_id>.txt` | 書類 1 通の本文。節ごとに見出しを付けてつないだもの。RAG にはこれを入れる |
| `docs.jsonl` | 書類ごとの会社名・EDINET コード・決算期と、各節の本文が `text/` のどこにあるか |
| `questions_ja.jsonl` | 設問・正解・正解の数値が印字された場所 |
| `chunks.jsonl` | 論文の索引と同じ区切りのチャンク（800 字ずつ 150 字重ね）の位置 |
| `MANIFEST.json` | 取得した版・元ファイルの SHA-256・検査の数 |

EDINET-Bench の XBRL の数値（`bs`・`pl`・`cf` の欄）は書き出しません。
設問の正解はこの数値から作ったので、RAG に入れると答えを渡すことになるからです。

### 3. 自分の RAG で解かせて記録する

174 問を自分の RAG に解かせ、1 行 1 問の JSON Lines に記録します。

```json
{"id": "JA_LOOKUP_0000", "chunks": [{"doc_id": "S10056GN", "text": "……"}], "value": "245,896百万円"}
```

- `chunks`：回答モデルに渡したチャンクを、渡した順に並べます。`doc_id` は `docs.jsonl` の書類の番号です。チャンクの区切り方は自由です。
- `value`：回答の値です。単位を別の欄に分けているなら、`"unit": "百万円"` を足してください。
- `get_ja_data.py` と同じ区切り方のチャンクなら、`{"chunk_id": "S100G299#3"}` と番号だけでも書けます。

### 4. 採点する

```bash
python rrm_ja.py --score run.jsonl --data ja_data
```

何も渡さずに全問「見つかりませんでした」と答えた記録なら、次のように出ます。

```
設問 174 問（JA-LOOKUP は全 174 問）
                  正答  無回答    誤答
届いた               0       0       0
届かなかった         0     174       0
正答率 0.000
検索で失敗（届かずに正答できない）1.000・読解で失敗（届いたのに正答できない）0.000
差（検索 − 読解）+1.000、95% 区間 [+1.000, +1.000] → まず直す場所: 検索
```

`--out rows.jsonl` を付けると、設問ごとの Reach（最初に正解の箇所が現れた順位）と Read を書き出します。

## 自分の RAG をほかと比べるときの決まり

- 174 問を全部回してください。設問を選ぶと比べられません。
- 正答率と一緒に、六つのマス・回答モデルの名前・渡したトークン数を書いてください。
  渡す量が多いほど正解の箇所は届きやすくなるので、件数ではなく分量でそろえます。
- 実行記録を公開すれば、誰でも同じ数字を出し直せます。

## 比較相手

自分の RAG の行を並べるための比較相手です。実行記録は `baselines/` にあり、次のように採点し直せます。

```bash
python rrm_ja.py --score baselines/fused_k7_gemini.jsonl --data ja_data
```

|---|---|---|---|---|---|---|---|---|---|
| 密ベクトル | 7 件（2.9K） | gemini-3.5-flash | 78.2% | 129 | 0 | 7 | 26 | 12 | 検索 |
| 密ベクトル | 7 件（2.9K） | gpt-5.4-mini | 57.5% | 100 | 29 | 0 | 0 | 45 | 決められない |
| 密ベクトル | 7 件（2.9K） | claude-sonnet-5 | 74.1% | 127 | 2 | 2 | 32 | 11 | 検索 |
| 融合 | 7 件（3.1K） | gemini-3.5-flash | 44.3% | 71 | 1 | 6 | 66 | 30 | 検索 |
| 融合 | 7 件（3.1K） | gpt-5.4-mini | 27.6% | 46 | 26 | 2 | 1 | 99 | 検索 |
| 融合 | 7 件（3.1K） | claude-sonnet-5 | 42.5% | 70 | 2 | 4 | 70 | 28 | 検索 |
| 融合 | 175 件（90K） | gemini-3.5-flash | 98.9% | 172 | 0 | 0 | 1 | 1 | 決められない |
| 融合 | 175 件（90K） | gpt-5.4-mini | 86.2% | 150 | 22 | 0 | 0 | 2 | 読解 |
| 融合 | 175 件（90K） | claude-sonnet-5 | 97.1% | 169 | 3 | 0 | 0 | 2 | 決められない |

渡した量の括弧内は、プロンプト全体の平均トークン数（o200k）です。正解の箇所が届いた設問は、密ベクトル検索の 7 件で 74%・融合検索の 7 件で 41%・175 件で 99% でした。
「届かずに正答」は、渡したチャンクのどこにも値が無いのに正答した設問です。回答モデルが値を覚えていたと考えられます。

作り方は次のとおりです（2026 年 10 月）。

- 書類とチャンクの区切り方は `get_ja_data.py` と同じです。各チャンクの頭に「会社名 決算期 有価証券報告書｜節名（期）」の見出しを付けて索引を作りました。
  表のチャンクには会社名が書かれていないので、見出しが無いと正解の箇所はほとんど届きません。
- 検索には設問の文をそのまま使いました。密ベクトル検索の埋め込みは multilingual-e5-small です。
  融合検索は、密ベクトル検索と BM25（fugashi で分かち書き）の順位を RRF（定数 60）で合わせたものです。
- プロンプトは、設問・指示・検索した文書（`---` で区切る）の順です。指示は「（決算期）について答えよ。別の期について答えた場合は、その期を `period_used` に書くこと。JSON だけを返すこと。`value` には金額を一つだけ、単位を付けて書くこと（例：「12,345百万円」）。」です。
  回答は `value`・`period_used`・`source`・`answer` の欄を持つ JSON で受け取り、温度は各 API の既定のままにしました。
- `baselines/` の実行記録は、渡したチャンクを番号で書いています。採点は見出しを除いた本文で行いますが、見出し付きで数えた結果と同じになることを確かめています。

## 規則の確かめ

```bash
python rrm_ja.py --selftest          # 手で作った 58 例
python rrm_ja.py --check ja_data     # 174 問の正解の位置と、正解の値から作った 791 通りの回答
```

`--check` では二つのことを確かめます。一つは、174 問すべてで、正解の数値の位置を含むチャンクを正解の箇所と数えることです。
もう一つは、Read が正しい書き方（表示単位どおり・億円に丸めたもの）を正答に、間違った書き方（単位違い・符号の抜け・最後の桁の違い）を誤答に分けることです。
